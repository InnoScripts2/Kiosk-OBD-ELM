# План тестирования доступности

Дата обновления: 2025-11-22  
Версия: 1.0  
Связанные документы: `plan-ux.md` (UI требования), `plan-ux` (если документ отсутствует — добавить), `plan-testing.md`, `plan-accessibility-guidance.md` (будет доработан), `plan-offline-resilience.md`, `plan-localization.md`, `plan-support-operations.md`

## 1. Цели и границы
- Подтвердить соответствие Android-киоска принципам WCAG 2.1 AA, локальным нормам (ГОСТ Р 52872-2019), внутренним UX-гайдлайнам.
- Охватить все критические пользовательские пути: onboarding, подключение адаптера, запуск диагностики, отчёты, оплата, поддержка.
- Обеспечить воспроизводимый процесс тестирования, автоматизацию ключевых проверок и трассировку дефектов в runbooks.

Вне зоны: изменение бизнес-логики, контент маркетинговых страниц, бэкенд Supabase.

## 2. Стандарты и критерии
| Категория   | Обязательные нормы                                                      | Критерии Pass/Fail                                                                                                   |
| ----------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Визуальная  | WCAG 1.4.x (контраст, адаптация текста), Android Material accessibility | Контраст текста ≥ 4.5:1, поддержка масштабирования шрифта 1.2×, отсутствие фиксированной ориентации при доступности. |
| Аудиальная  | WCAG 1.2.x, Android TalkBack guidelines                                 | Все важные уведомления дублируются визуально, озвучены `contentDescription`.                                         |
| Моторика    | WCAG 2.1.1 / 2.1.2, Switch Access                                       | Активные области ≥ 48dp, все действия доступны без жестов multi-touch.                                               |
| Когнитивная | WCAG 3.1/3.2, Plain language                                            | Инструкции не зависят от цвета, текст ≤ 8 строк на экран, последовательность шагов стабильна.                        |

## 3. Матрица охвата по сценариям
| Сценарий                      | Риски доступности                                     | Метрики                                                      | Частота                               |
| ----------------------------- | ----------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------- |
| A1 — Onboarding/MDM тревоги   | Неправильные фокусы, скрытые предупреждения           | Кол-во критических фокус-ловушек = 0                         | Каждый релиз                          |
| A2 — Подключение BLE адаптера | Таймеры без озвучки, маленькие кнопки                 | Размер кнопок ≥ 48dp, VoiceOver проговаривает прогресс       | Каждая фича-ветка                     |
| A3 — Диагностика и статусы    | Динамический контент без LiveRegion                   | `aria-live=polite` эквивалент (Compose `LiveRegion`) включён | Каждое обновление Diagnostics runtime |
| A4 — Отчёты и платежи         | Некорректный порядок табов, отсутствие alt в графиках | Порядок табов совпадает с визуальным, графики имеют текст    | Каждое изменение шаблонов отчёта      |
| A5 — Оффлайн/ошибки           | Ошибка только текст/цвет                              | Сообщения сопровождаются иконкой и озвучкой                  | Каждая ревизия runbook                |

## 4. Подготовка окружения
1. **Аппарат**: планшет в киоске + запасной dev-планшет, Bluetooth-клавиатура, Switch Access пульт, наушники.  
2. **ПО**: Android 12+, TalkBack 13, Switch Access 13, Accessibility Scanner, Espresso `AccessibilityChecks`, Firebase Test Lab (виртуальные устройства).  
3. **Данные**: демо-аккаунт Supabase QA, тестовые VIN, контрольные DTC из `plan-diagnostics-data-pipeline.md`.  
4. **Конфигурация**: dev-флаг `ACCESSIBILITY_DEBUG` включает наложение фокуса и логирование события `a11y_focus_changed` в telemetry.

## 5. Процесс тестирования
1. **Подготовка (T-2 дня)**: проверить актуальность чек-листов, обновить TalkBack словарь, синхронизировать дизайны (`plan-ux`).
2. **Автотесты (T-1 день)**: 
   - `./gradlew :app:connectedDebugAndroidTest --tests "*Accessibility*"` — Espresso тесты со включёнными `AccessibilityChecks`.
   - `./gradlew :feature-obd-core:testDebugUnitTest --tests "*Semantics*"` — unit-проверки Compose семантики.
3. **Ручные проверки (T день)**: чек-листы по категориям (см. раздел 6). Каждая проблема логируется с приоритетом и скринкастом.
4. **Регресс после фиксов (T+1)**: повтор автотестов + targeted manual cases.
5. **Отчёт (T+2)**: обновление `plan-testing.md` с результатами, создание тикетов в Jira категории `Accessibility`.

## 6. Чек-листы
### 6.1 Визуальный доступ
- Контраст проверяется Accessibility Scanner + `ColorContrastAnalyzer`.  
- Масштабирование системного шрифта 200%: приложения не ломают layout, скролл доступен.  
- Темная тема: отсутствуют элементы с прозрачным текстом.

### 6.2 Экранные читатели
- TalkBack: порядок фокуса совпадает с визуальным, элементы объединены через `mergeDescendants = true` только при необходимости.  
- Прогресс-бары и таймеры используют `LiveRegion`.  
- Отсутствуют пустые `contentDescription`.  
- Проверка BrailleBack (ЕУ требования): все основные сценарии читаемы.

### 6.3 Управление без касания
- Switch Access: пройти сценарии A1–A4 только кнопками `Next/Select`.  
- Поддержка аппаратной клавиатуры (Tab/Enter/Esc).  
- Жесты (swipe) имеют альтернативу (кнопка, таймер).

### 6.4 Когнитивные требования
- Тексты проверены на понятность (уровень B1, синонимы технических терминов).  
- Подсказки не исчезают автоматически без подтверждения.  
- Ошибки содержат шаги исправления и ссылку «Нужна помощь».

## 8. Метрики и отчётность
- `a11y_violations_total{severity}` — экспорт из автотестов.  
- `a11y_manual_defects_open` — количество незакрытых дефектов > 7 дней.  
- KPI релиза: 0 блокирующих дефектов, ≤3 минорных, время фикса критического ≤ 2 рабочих дня.  
- Отчёты хранятся в Supabase таблице `accessibility_reports` + ссылка в `plan-testing.md`.

## 9. Ответственности
| Роль                   | Обязанности                                                            |
| ---------------------- | ---------------------------------------------------------------------- |

| Android Team           | Реализует фиксы, покрывает автоматическими тестами.                    |
| QA Accessibility Owner | Ведёт чек-листы, проводит ручные проверки, подтверждает дефекты.       |
| Support/Ops            | Обновляет runbooks `plan-support-operations.md` при жалобах клиентов.  |

## 10. Полевое подтверждение
- Раз в квартал тестирование на реальном киоске с участием пользователей из фокус-группы (по договорам).  
- Сбор обратной связи через `plan-customer-feedback.md` формы, метрики NPS доступны по сегменту «Accessibility».  
- Логи `a11y_focus_changed` анализируются на предмет зависаний.
